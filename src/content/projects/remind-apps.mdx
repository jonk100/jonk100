## Technical Architecture: The Two-Tier State Management Engine

A major challenge in dynamic, modern web applications is managing complex state. As users log habits, journal, and edit notes, we must synchronize records with a Supabase database. Standard architectures often suffer from:
* **Brittle Boolean Flags**: Using multiple boolean states (`isLoading`, `isError`, `isSaving`) which leads to "impossible states" (e.g. showing a loading spinner while simultaneously displaying a network error).
* **UI Hydration Lag**: Waiting for database round-trips to complete before updating the user interface.

To solve this, re:MindMatters implements a sophisticated **two-tier state management architecture** separating business logic flow from layout bindings:

```
+--------------------------------------------------------+
|                      XState v5                         |
|   (The Engine: Asynchronous flows, autosave sync,      |
|    retry loops, strict state transitions, rollbacks)   |
+---------------------------+----------------------------+
                            |
                            v  Pushes state updates
+--------------------------------------------------------+
|                     NanoStores                         |
|   (The Display: Global UI state, reactive variables,   |
|    filtered lists, reactive counts, lightweight islands)|
+--------------------------------------------------------+
```

### 1. The Asynchronous Flow Engine (XState v5)
We use **XState v5** to manage complex, multi-step asynchronous processes. XState models user flows as finite state machines, guaranteeing that transitions only occur in response to explicit actions and orchestrating background syncs, retry loops, and local rollbacks if network requests fail:

```typescript
// Excerpt from habits store state machines
import { setup, createMachine, assign } from 'xstate';

export const habitMachine = setup({
  types: {
    context: {} as { habits: Habit[]; error: string | null },
    events:
      | { type: 'FETCH_HABITS' }
      | { type: 'LOG_HABIT'; id: string }
      | { type: 'RETRY' },
  },
  actions: {
    optimisticUpdate: assign({
      habits: ({ context, event }) => {
        // Log habit locally and immediately in client UI
        return context.habits.map(h => 
          h.id === event.id ? { ...h, completedToday: !h.completedToday } : h
        );
      }
    })
  }
}).createMachine({
  id: 'habitTracker',
  initial: 'loading',
  states: {
    loading: {
      invoke: { src: 'fetchHabits', onDone: 'idle', onError: 'error' }
    },
    idle: {
      on: { LOG_HABIT: { target: 'syncing', actions: 'optimisticUpdate' } }
    },
    syncing: {
      invoke: {
        src: 'syncSupabase',
        onDone: 'idle',
        onError: 'rollback' // Handles connection failure gracefully
      }
    },
    error: {
      on: { RETRY: 'loading' }
    }
  }
});
```

### 2. The Reactive Display Cache (NanoStores)
Rather than forcing our UI components to subscribe to heavy state machines, we use **NanoStores** as a lightweight, reactive display layer. NanoStores holds active IDs, filters, and global UI states, deriving values like live document word counts on-the-fly:

```typescript
// Excerpt from src/stores/editor.ts
import { map, computed } from 'nanostores';

export interface EditorState {
  documentId: string | null;
  blocks: Block[];
  isDirty: boolean;
  isSaving: boolean;
}

export const editorStore = map<EditorState>({
  documentId: null,
  blocks: [],
  isDirty: false,
  isSaving: false,
});

// Calculate word counts instantly during typing
export const wordCount = computed(editorStore, (s) =>
  s.blocks.reduce((acc, b) => acc + (b.content?.trim().split(/\s+/).filter(Boolean).length || 0), 0)
);
```

Other interface islands (like counters, toolbar indicators, and sidebars) subscribe directly to these lightweight stores, keeping them completely decoupled from the internal mechanics of the background XState machines.

## Custom Headless TipTap Rich-Text Editor (`TipTop.astro`)

The journaling core of re:MindMatters requires a distraction-free writing experience. Traditional text fields and textareas are too restrictive, while standard WYSIWYG editors are bloated and inject ugly inline styles that violate content semantics.

To build a premium journaling tool, we developed **TipTop**—a highly customized, headless editor built on top of the **TipTap** core:

* **Block-Based Structure**: Instead of a single text stream, content is represented as an array of structured blocks.
* **Seamless Keyboard Traversal**: Custom keymap extensions intercept standard actions:
  * Pressing `Enter` splits the current paragraph block, creating a new block below.
  * Pressing `Backspace` on an empty block merges it back with the preceding block.
* **Visual State Hookup**: As the user types, the custom toolbar and page margin components react dynamically to active block cursors, providing immediate formatting controls (bold, italic, checklists, and headings).

The editor communicates block mutations directly to the local `editorStore` NanoStore, which in turn feeds the XState compiler to debounce and trigger background autosaves.

## Type-Safe Backend Astro Actions & Supabase Sync

Data mutations (creating habits, logs, and notes) are orchestrated via **Astro Actions**—Astro's type-safe backend framework. Astro Actions acts as a secure bridge between client UI components and the Supabase database:

```typescript
// Excerpt from src/actions/habit.actions.ts
import { defineAction, ActionError } from "astro:actions";
import { z } from "astro:zod";
import { createClient } from "@/lib/supabase";
import { recalculateStreak } from "@/lib/habit/streak";

export const habit = {
  upsertLog: defineAction({
    input: z.object({
      habit_id: z.uuid("Invalid habit ID"),
      entry_date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/, "Date must be YYYY-MM-DD"),
      value: z.number().optional(),
    }),
    handler: async (input, context) => {
      // 1. Authenticate session securely server-side
      const { supabase, user } = await getAuthenticatedUser(context);

      // 2. Perform optimistic upsert (insert or update log entry)
      const { data, error } = await upsertHabitLog(supabase, {
        habit_id: input.habit_id,
        entry_date: input.entry_date,
        value: input.value ?? null,
        user_id: user.id,
      });

      if (error) {
        throw new ActionError({
          code: "INTERNAL_SERVER_ERROR",
          message: error.message,
        });
      }

      // 3. Recalculate streak values dynamically on Postgres
      const streak = await recalculateStreak(supabase, input.habit_id, user.id, input.entry_date);

      return { ...data, streak };
    },
  }),
};
```

This guarantees end-to-end type safety: Zod validates user inputs in the API layer, and TypeScript enforces contracts from client components to the Supabase client under Postgres **Row-Level Security (RLS)** constraints.
