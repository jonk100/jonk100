A **Token** is a structured, categorized object representing the smallest indivisible unit of meaning in a programming language's source code.

It is the primitive atomic currency of compilers, interpreters, syntax highlighters, and linters. Before a machine can understand the structural logic of code, it must first recognize the raw individual words and symbols.

To understand tokens properly, you need to see how code looks to a computer before it is tokenized, how text is split apart, and why standard text tools aren't enough.

## Before Tokens: a raw stream of characters

To a human, code looks like a series of commands, variables, and structures. To a computer reading a source file, code is initially nothing more than a long, linear **stream of characters**.

Example:

```js
let count = 42;

```

A compiler looking blindly at this sees:

`l`, `e`, `t`, ` `, `c`, `o`, `u`, `n`, `t`, ` `, `=`, ` `, `4`, `2`, `;`

A raw compiler pipeline trying to parse meaning directly from characters would face intense issues:

* Differentiating if `let` is the keyword or the start of a variable named `lettuce`.
* Handling unpredictable formatting (e.g., `let  count=42  ;`).
* Identifying multi-character operators like `==`, `&&`, or `=>` versus individual characters.

### The core problem

Characters are too low-level. Programs are expressed in terms of concepts—keywords, identifiers, numbers, and operators. Trying to interpret logic character-by-character introduces immense structural noise.

---

## Lexical Analysis: breaking text into lexemes

The process of converting a character stream into a structured token stream is called **Lexical Analysis** (or tokenization), performed by a **Lexer** (or tokenizer).

The lexer scans characters sequentially and groups them into logical substrings called **lexemes**. It then pairs each raw lexeme with a semantic category to create a **token**.

For:

```js
let count = 42;

```

The lexer scans the text and spits out structured pairs:

* `let` $\rightarrow$ **Keyword (LET)**
* `count` $\rightarrow$ **Identifier (IDENT)**
* `=` $\rightarrow$ **Operator (ASSIGN)**
* `42` $\rightarrow$ **Literal (NUMBER)**
* `;` $\rightarrow$ **Punctuation (SEMICOLON)**

This abstraction strips away the individual character complexities, giving downstream tools a highly uniform sequence to process.

---

## Token Anatomy: What makes up a token?

In basic compiler architectures, a token is not just a string. It is typically a structured object containing multiple properties.

### Same example:

```js
count

```

A concrete token object in a compiler engine usually stores:

```
{
  type: "IDENTIFIER",
  value: "count",
  line: 1,
  column: 5,
  start: 4,
  end: 9
}

```

By keeping the metadata (`line`, `column`, etc.), tools can report highly precise error messages later on, like: `SyntaxError: Unexpected identifier 'count' at line 1, column 5`.

---

## Where Tokens fit in the compilation pipeline

Tokenization is step zero of code ingestion. It sits at the absolute gate of the compiler pipeline.

```
Source Code (Character Stream)
    ↓
Lexical Analysis (Lexer / Tokenizer)
    ↓
Tokens (Token Stream)
    ↓
Parsing
    ↓
AST (Abstract Syntax Tree)

```

### The Transition: Token stream to AST

While a **lexer** flattens the character code into a linear array of structural units (tokens), it has no understanding of structural hierarchy or grammar rules. It doesn't know if a token sequence makes actual sense.

The **parser** takes this linear stream of tokens and groups them into hierarchical tree structures.

For example, a token stream of `NUMBER(1), PLUS, NUMBER(2)` is assembled by the parser into a tree structure capturing the operation:

```
   + (Operator Node)
  / \
 1   2 (Literal Nodes)

```

## Why Tokens are so important

Standardizing code into a clean stream of tokens enables modern software development ecosystems to function smoothly.

### Tokens power Syntax Highlighting

Your text editor (like VS Code) uses a high-speed lexer to instantly convert code to tokens. Once it identifies that `let` is a `Keyword` and `count` is an `Identifier`, it instantly assigns CSS theme colors to those specific text segments. It doesn't need to parse the whole application logic to color-code it.

---

### Tokens enable robust Linting

Linters scan token streams to find localized violations or code smells. For example, a linter might look for the specific sequence of two concurrent tokens like `INCREMENT (++), INCREMENT (++)` to warn you about highly volatile expressions before it even compiles.

---

### Tokens simplify Parser Code

Writing a parser that reads raw characters is incredibly difficult and messy. By offloading the character grouping to a dedicated lexer, the parser code can focus exclusively on macro structural grammar (e.g., "An IF statement token must always be followed by a OPEN_PAREN token").

## Comparisons - Token vs Related Concepts

### Lexeme vs Token

| Term | What it is | Example |
| --- | --- | --- |
| **Lexeme** | The raw string sequence found in source code. | `"count"`, `"+"`, `"42"` |
| **Token** | The conceptual classification + the lexeme. | `IDENTIFIER("count")`, `ASSIGN("=")` |

---

### Token vs AST Node

* **Token** = A linear, atomic building block. It has no children. It represents basic lexical items.
* **AST Node** = A composite structural component of a tree. It can contain other nodes or tokens (e.g., an `IfStatement` node contains a condition node and a body node).

---

## Technical Implementations of Lexers

Most modern lexers rely on underlying state machines driven by **Regular Expressions**.

For instance, a lexer might define basic rules like:

* Numbers: `/[0-9]+/`
* Identifiers: `/[a-zA-Z_][a-zA-Z0-9_]*/`
* Whitespace: `/\s+/` (which it typically chooses to discard so the parser doesn't have to deal with blank spaces).

---

## Related terms (glossary cluster)

### Lexer / Tokenizer

The engine module tasked with consuming text and producing tokens.

### Scanning

The act of reading characters one-by-one to discover bound elements.

### Whitespace Stripping

The process where a lexer discards blank spaces, tabs, and line breaks to minimize data noise for the parser.

### Keyword

A reserved word (like `for`, `while`, `class`) categorized as a unique type of token that cannot be used as a variable name.

## Mental model summary

If you compress everything:

* Characters are raw atoms.
* Tokens are organized molecules.
* ASTs are full complex structures built out of those molecules.

A useful analogy:

* Characters = Individual alphabet letters (`c`, `a`, `t`)
* Tokens = Valid individual words dictionary lookup types (`Noun("cat")`)
* AST = A complete, structured sentence layout diagram.

## Custom Tokenizer Code Example

Below is a minimal **hand-written Tokenizer in TypeScript**. It demonstrates the foundational pipeline step: iterating through an incoming string of characters and converting it into a clean stream of strongly-typed tokens.

---

# 1. Token Types (`types.ts`)

```ts
/**
 * Types defining the available tokens in our language.
 */

export type TokenType =
  | "KEYWORD"
  | "IDENTIFIER"
  | "NUMBER"
  | "OPERATOR"
  | "PUNCTUATION";

export interface Token {
  type: TokenType;
  value: string;
  line: number;
  column: number;
}

```

---

# 2. Tokenizer Implementation (`tokenizer.ts`)

```ts
import { Token, TokenType } from "./types";

const KEYWORDS = new Set(["let", "const", "var", "if", "else", "return"]);
const IS_NUMBER = /[0-9]/;
const IS_ALPHA = /[a-zA-Z_]/;
const IS_ALPHANUM = /[a-zA-Z0-9_]/;

export function tokenize(sourceCode: string): Token[] {
  const tokens: Token[] = [];
  let cursor = 0;
  let line = 1;
  let column = 1;

  while (cursor < sourceCode.length) {
    let char = sourceCode[cursor];

    // Track lines and handle whitespace
    if (char === "\n") {
      line++;
      column = 1;
      cursor++;
      continue;
    }

    if (/\s/.test(char)) {
      cursor++;
      column++;
      continue;
    }

    // Numbers (Literals)
    if (IS_NUMBER.test(char)) {
      let value = "";
      const startColumn = column;

      while (cursor < sourceCode.length && IS_NUMBER.test(sourceCode[cursor])) {
        value += sourceCode[cursor];
        cursor++;
        column++;
      }

      tokens.push({ type: "NUMBER", value, line, column: startColumn });
      continue;
    }

    // Identifiers & Keywords
    if (IS_ALPHA.test(char)) {
      let value = "";
      const startColumn = column;

      while (cursor < sourceCode.length && IS_ALPHANUM.test(sourceCode[cursor])) {
        value += sourceCode[cursor];
        cursor++;
        column++;
      }

      const type: TokenType = KEYWORDS.has(value) ? "KEYWORD" : "IDENTIFIER";
      tokens.push({ type, value, line, column: startColumn });
      continue;
    }

    // Operators
    if ("+-*/=".includes(char)) {
      tokens.push({ type: "OPERATOR", value: char, line, column });
      cursor++;
      column++;
      continue;
    }

    // Punctuation
    if (";,(){}".includes(char)) {
      tokens.push({ type: "PUNCTUATION", value: char, line, column });
      cursor++;
      column++;
      continue;
    }

    throw new SyntaxError(`Unexpected character '${char}' at line ${line}, column ${column}`);
  }

  return tokens;
}

```

# 3. Usage (`index.ts`)

```ts
import { tokenize } from "./tokenizer";

const code = `let limit = 100;`;
const tokenStream = tokenize(code);

console.log(JSON.stringify(tokenStream, null, 2));

```

# 5. What this tiny tokenizer demonstrates

* **Lossless grouping:** Characters like `1`, `0`, and `0` are compressed safely into one distinct entity (`100`).
* **Categorization:** It distinguishes user variables (`limit`) from embedded engine instructions (`let`).
* **Positional Tracking:** Contextual positional data remains pinned for upstream tooling diagnostics.

## Review

Before moving on to parsing and higher-level compiler design, keep these foundational token concepts in mind:

* **Tokens are flat:** A token stream has no nested depth, no parenting hierarchies, and no execution logic. It is purely a 1D sequence of identified words.
* **Lexemes vs. Tokens:** The raw text string itself is the *lexeme* (e.g., `"+"`); the object classification that gives it meaning to a compiler is the *token* (e.g., `OPERATOR`).
* **The Parser's dependency:** A parser cannot do its job without a tokenizer. If you feed a parser raw character bytes instead of categorized tokens, your parsing logic will quickly collapse under structural noise.
* **Metadata is vital:** Tokens don't just hold code values; they retain spatial position data (lines, columns, character offsets). This tracking is why your IDE knows exactly where to put a red wavy underline when you miss a closing bracket.
