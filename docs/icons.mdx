Given the editorial, token-driven system you've described, I'd avoid literal icons (paper sheets, chains, image landscapes, etc.). Those tend to feel generic and age poorly.

Instead, I'd build a consistent icon language around **composition primitives**:

| Component | Concept      | Shape                     |
| --------- | ------------ | ------------------------- |
| Paper     | Surface      | Single rectangle          |
| Frame     | Container    | Double rectangle          |
| Image     | Visual media | Rectangle + mountain line |
| Link      | Connection   | Two linked nodes          |
| Text      | Typography   | Horizontal text lines     |

All icons:

* 24×24 viewBox
* 1.75 stroke width
* rounded caps/joins
* monochrome
* minimal geometry
* no fills

If you plan to eventually have 30–50 primitives (Stack, Inline, Grid, Divider, Avatar, Heading, Badge, Skeleton, Spinner, etc.), I'd recommend building the entire icon set around a **geometric composition language**:

* rectangles = surfaces
* lines = flow
* circles = entities
* nested shapes = containment
* spacing = layout

That produces a much more cohesive library than mixing common UI icons from different visual traditions.
